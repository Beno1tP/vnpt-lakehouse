| E25 | After `minikube start --memory=8192`: node `Allocatable` memory = **11217116Ki (10.7 GiB)** and `cpu: 8`, although `docker inspect minikube` shows `HostConfig.Memory=8589934592` (8 GiB) and the node's `/sys/fs/cgroup/memory.max` = 8589934592 (2026-10-25, *seen*) | With the docker driver the kubelet reads capacity from the shared WSL kernel (`/proc/meminfo`), not from the container's cgroup limit. The scheduler therefore admits pods up to 10.7 GiB of requests while the real cap is 8 GiB → whole-node OOM instead of `Pending`. CPU: `CpuQuota=0`, so all 8 CPUs are usable (not a problem: RAM is the bottleneck) | Recreate the (still empty) cluster with `--extra-config=kubelet.system-reserved=memory=3686Mi` → Allocatable = 10954 − 3686 − 100 (eviction) = **7168 Mi**; the kubelet then caps the `kubepods` cgroup at 7168 Mi, leaving ~1 GiB of the 8 GiB for kubelet/containerd | Allocatable = Capacity − kube-reserved − system-reserved − eviction-threshold; with `enforceNodeAllocatable=[pods]` (default) the kubelet sets the pods cgroup limit to Allocatable. Requests are only as safe as the capacity the kubelet believes | fix proposed |
