| E25 | After `minikube start --memory=8192`: node `Allocatable` memory = **11217116Ki (10.7 GiB)** and `cpu: 8`, although `docker inspect minikube` shows `HostConfig.Memory=8589934592` (8 GiB) and the node's `/sys/fs/cgroup/memory.max` = 8589934592 (2026-10-25, *seen*) | With the docker driver the kubelet reads capacity from the shared WSL kernel (`/proc/meminfo`), not from the container's cgroup limit. The scheduler therefore admits pods up to 10.7 GiB of requests while the real cap is 8 GiB → whole-node OOM instead of `Pending`. CPU: `CpuQuota=0`, so all 8 CPUs are usable (not a problem: RAM is the bottleneck) | Recreate the (still empty) cluster with `--extra-config=kubelet.system-reserved=memory=3686Mi` → observed Allocatable **7442652Ki (7268 Mi)** = 11217116Ki − 3686 Mi (minikube sets `evictionHard` to `0%`, so no 100 Mi eviction margin is subtracted, unlike stock kubelet); node `kubepods.slice/memory.max` = 7621275648 bytes = the same 7268 Mi → pods are capped, ~0.9 GiB of the 8 GiB stays for kubelet/containerd | Allocatable = Capacity − kube-reserved − system-reserved − eviction-threshold; with `enforceNodeAllocatable=[pods]` (default) the kubelet sets the pods cgroup limit to Allocatable. Requests are only as safe as the capacity the kubelet believes | fixed (cluster recreated 2026-10-25) |
| E26 | Guide's check command → `ERROR: syntax error at or near "\"` … `IN (\x27metast…` (2026-10-25, *seen*) | Claude wrote `\x27` for a single quote inside `sh -c '… "…" …'`; neither sh double quotes nor psql interpret `\x27` | Query without string literals (`WHERE NOT datistemplate`) | Quoting layers: kubectl → sh -c (single) → psql -c (double) → SQL (single). Avoid literals or use `$$…$$`/a file instead of escaping | fixed |
| E27 | `psql -h postgres.lake.svc.cluster.local -U airflow` → `FATAL: password authentication failed for user "airflow"`; pod log: `cat: /run/secrets/pg/AIRFLOW_DB_PASSWORD: Permission denied`, `NOTICE: empty string is not a valid password, clearing password`, then `airflow role and database created`; `pg_authid`: airflow `rolpassword IS NULL` (2026-10-25, *seen*) | Secret volume files were `root:root 0400`; the image's entrypoint reads `POSTGRES_PASSWORD_FILE` **as root** (before `gosu postgres`), but runs `/docker-entrypoint-initdb.d/*` **as postgres (uid 999)**, so `cat` failed. `$(cat …)` inside a command argument does not trigger `set -e`, so the script went on with an empty password and reported success | Pod `securityContext.fsGroup: 999` + secret `defaultMode: 0440`; script reads the file in a separate assignment (`set -e` applies) and refuses an empty value. Init scripts run only on an empty data dir → delete the StatefulSet + PVC (empty DB) and recreate | Secret volumes are owned by root unless `fsGroup` sets the group; know which user each step of an entrypoint runs as. Bash: `set -e` ignores failures inside command substitutions used as arguments; assign first, then use. A success message is not proof: test the real path (network login) | fixed: re-init 2026-10-25, files `-r--r----- 0 999`, network login `airflow\|airflow` |
